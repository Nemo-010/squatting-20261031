# Content hosting on a borrowed web server

Scope: your IP as the *page hoster* of somebody else's stack — a compromised or repurposed web server on a host you pay for, serving pages you did not author: phishing landings, kit downloads, redirect chains, staged payloads, and the C2 pull-home that documented malware front-ends do from a WordPress site. Detection is host-side and priced by the cheapest tiers: access logs first, then the document root, then long-standing web-shell guides. What is NOT here: relays and reflectors (`open-relays-amplification-reflectors.md` owns that), and the external-only views — Certificate Transparency, passive DNS, honeypots — which `external-vantage-and-honeypots.md` owns. Every path, port and default below was verified from a primary source this session; anything unverifiable is in [What I could not verify](#what-i-could-not-verify).

## Summary

- **One provider's malware operation ran ~2,000 hacked WordPress domains as payload host + C&C + exfil storage (>6,000 unique victim IPs as of 2026-07-24)** — on-host tells include `wp-content/mu-plugins/wp-sec.php` (hidden REST endpoint `wp-json/wp-sec/v1/upload`, hardcoded creds, allows `.php` upload → RCE) and `wp-content/plugins/verify/` (<https://research.checkpoint.com/2026/thousands-of-hacked-wordpress-sites-one-operation-unmasking-stopandprotect/>).
- **A phishing kit can be nothing but PHP files in a WordPress docroot**: Fortra's RatPressto kit (2026) staged byte-identical pages on multiple compromised WordPress sites — `download.html`, `complete.php`, `download.php` — with a hidden `<iframe src="download.php" style="display:none;">` and exposed `/wp-admin/` (<https://fortra.com/blog/ratpressto-phishing-kit>).
- **The access log is the first ledger, and it is on your disk**: Debian's packaged nginx.conf sets `access_log /var/log/nginx/access.log;` (<https://sources.debian.org/src/nginx/1.26.3-3%2Bdeb13u7/debian/conf/nginx.conf>); Ubuntu Apache writes `/var/log/apache2/access.log` (<https://ubuntu.com/server/docs/how-to/web-services/configure-apache2-settings/>); RHEL vhosts show `CustomLog /var/log/httpd/example.com_access.log combined` (<https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/10/html/deploying_web_servers_and_reverse_proxies/setting-up-the-apache-http-web-server>).
- **The one-line page-shape check is field 7 of the CLF line** — `grep -E 'HTTP/1\.[01]"' /var/log/nginx /var/log/apache2 /var/log/httpd -r | awk '{print $7}' | sort | uniq -c | sort -rn | head -20` — the `$7` isolation hand-tested 2026-11-01 on a synthetic CLF file against `/wp-content/uploads/2025/11/sh.php`; the grep there was the strict `'HTTP/1.1"'` form, which misses HTTP/1.0 request lines, so the recipe below ships the `-E 'HTTP/1\.[01]"'` form.
- **A `.htaccess` payload survives with no PHP at all**: `AccessFileName` defaults to `.htaccess`, and the server reads it "in every directory of the path to the document" (<https://httpd.apache.org/docs/2.4/mod/core.html#accessfilename>); WordPress can only overwrite between its own `# BEGIN WordPress` markers, so attacker rules sit outside them (<https://developer.wordpress.org/advanced-administration/security/hardening/>).
- **`wp-content/mu-plugins` is the highest-signal WordPress directory to inventory**: files there are "automatically enabled on all sites", cannot be disabled from wp-admin, and "a compromised mu-plugin can be harder to notice than a normal plugin" (<https://developer.wordpress.org/advanced-administration/plugins/mu-plugins/>); the Check Point case abused exactly that directory.
- **`/.well-known/acme-challenge/` is a write-to-become-owner path**: RFC 8555 §10.2 warns that "on a web server that allows non-administrative users to write to .well-known, any user can claim to own the web server's hostname by responding to an HTTP challenge" (<https://rfc-editor.org/rfc/rfc8555.html>).
- **`.htaccess` payloads are gated by configuration, not just discoverable by sweep**: with the shipped `AllowOverride None` the server "will not even attempt to read" the file (<https://httpd.apache.org/docs/2.4/mod/core.html#allowoverride>); where override is widened — the usual WordPress host — a file read "in every directory of the path to the document" is in play again (Section 3's override gate).
- **AI-native edge platforms host the same content with no host to check**: Trend Micro (2025-09-19) counted 52 `vercel.app`, 43 `lovable.app`, 3 `netlify.app` sites serving fake-CAPTCHA pages since 2025-01 (<https://www.trendmicro.com/en_us/research/25/i/ai-development-platforms-enable-fake-captcha-pages.html>); Vercel, Netlify and Deno ban these uses in their AUPs, but every host-side check in this file is blind there — only CT/passive-DNS vantage can see it, which `external-vantage-and-honeypots.md` owns.
- **The honest limit**: a load-balanced share of legitimately forwarded traffic can reproduce the same log shape; the discriminating evidence is file-level — mtime vs ctime, which `checks/triage.sh` already implements (its D05 rule).

## 1. How a borrowed web server becomes a publishing node

A borrowed web server is reached by one of two routes, and both are invisible in the hosting contract. The first is a compromise: a WordPress installation or other PHP app whose admin surface was taken over, or an additional vhost enabled under an existing server (`sites-enabled/*` in Debian-family Apache; `include /etc/nginx/sites-enabled/*;` is verbatim from Debian's shipped nginx.conf). The second needs no breach at all: content published on an edge platform that never ran on your machine (Section 7). What lands on the host in the first case is page content you did not author, plus the scripts that serve it.

Three case studies with the same shape, from three different teams:

- **Check Point / "StopAndProtect" (2026-08-18)**: ~2,000 compromised WordPress domains used simultaneously as a payload host, C&C, and exfil storage; >6,000 unique victim IPs as of 2026-07-24 (US 1852, RU 630, IN 630); ~31,000 screenshots collected mid-May–end-July 2026. On-host artifacts: `wp-content/plugins/verify/` (`verify.php`, `store.php`, `proxy.php`, `stored_url.txt`), the must-use plugin `wp-content/mu-plugins/wp-sec.php` with a hidden REST route `wp-json/wp-sec/v1/upload` and hardcoded credentials that allowed a `.php` upload and thus RCE, a self-deleting installer `mu-uploader-installer.php`, dropped files `dwnen.php` and `vcapcha.ps1`, an edited `wp-config.php` (the `WP_CACHE` line removed), and a litespeed-cache deactivator. Windows visitors to the original sites got a fake-CAPTCHA ClickFix page overwriting the original content (<https://research.checkpoint.com/2026/thousands-of-hacked-wordpress-sites-one-operation-unmasking-stopandprotect/>).
- **Fortra's RatPressto (2026)**: a phishing kit deployed onto multiple compromised WordPress sites, pages byte-identical across victims — the kit ships `download.html`, `complete.php`, `download.php` into WordPress-accessible directories, hides the delivery inside `<iframe src="download.php" style="display:none;">`, chains to a ScreenConnect C2 (`cloud.zistopstoabetterlife.com:8041`), and blocks known scanner IPs and user-agents with redirects to a real easternbank.com page (<https://fortra.com/blog/ratpressto-phishing-kit>).
- **Trend Micro (2025-09-19)**: fake-CAPTCHA pages on AI-platform builders — 52 `vercel.app`, 43 `lovable.app`, 3 `netlify.app` — the edge case this file's host-side checks cannot reach (Section 7).
- **The pull-home, the same sites in reverse**: the Check Point operation used the hacked sites as a collection point too — server-side artifacts `store.php`, `proxy.php` and `stored_url.txt` sat under `wp-content/plugins/verify/`, and the mu-plugin's hidden REST route `wp-json/wp-sec/v1/upload` accepted uploads with hardcoded credentials. One domain set served in both directions: phishing content out, uploads and stored state in (<https://research.checkpoint.com/2026/thousands-of-hacked-wordpress-sites-one-operation-unmasking-stopandprotect/>).

The common property of all three cases: the operator never needed to administer the machines. Whether access came from a stolen WordPress admin session, an unlocked vhost, or an edge-platform account, the published content is front-end infrastructure for a chain that the machine's owner does not control. That is why the host can be read from outside as an I-own-you ledger but the fastest inside evidence is local: the access log (Section 2), then the document root (Section 3).

> The kit-level lesson from Fortra's writeup: staged pages share identical bytes across victims, and the campaign's `/wp-admin/` was publicly reachable on all of them. Neither property requires any login on the assets the kit rented for hosting, which is exactly why the checks here can be cheap.

## 2. The access log: the first ledger, tested line by line

**Where the logs are.** Debian's `nginx.conf` ships with `access_log /var/log/nginx/access.log;` and `error_log /var/log/nginx/error.log;` (<https://sources.debian.org/src/nginx/1.26.3-3%2Bdeb13u7/debian/conf/nginx.conf>). The `nginx-common` package also ships `/etc/logrotate.d/nginx` (<https://packages.debian.org/trixie/all/nginx-common/filelist>). Ubuntu's Apache2 docs name `/var/log/apache2/access.log` as the default transfer log, with per-site logs overridable via `CustomLog` (<https://ubuntu.com/server/docs/how-to/web-services/configure-apache2-settings/>); the Debian `apache2` package ships the log-rotation file `/etc/logrotate.d/apache2` (<https://packages.debian.org/trixie/all/apache2/filelist>). Red Hat's RHEL 10 guide shows per-vhost `CustomLog /var/log/httpd/example.com_access.log combined` and names `/etc/httpd/conf/httpd.conf` as the main configuration (<https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/10/html/deploying_web_servers_and_reverse_proxies/setting-up-the-apache-http-web-server>).

**Per-vhost logging, and why your own vhost's log is not the whole story.** Apache's `CustomLog` and `ErrorLog` are settable per-vhost: the RHEL 10 vhost example above shows exactly that pattern, and the Ubuntu doc says the transfer log is changeable "on a per-site basis in your virtual host configuration files with the **CustomLog** directive". A squatted vhost can therefore be logged to a file your default-log sweep never touches — enumerate every site, not just the server's default log. Apache's logs doc also names the `%v`-based split (`split-logfile`) as the mechanism a mass-vhost host uses to separate per-site histories (<https://httpd.apache.org/docs/2.4/logs.html>). The fact your `find` turns up these files (or turns up none where logging should exist) is itself a triage answer.

**The line format.** The Common Log Format line is space-separated with the time bracketed: `127.0.0.1 - frank [10/Oct/2000:13:55:36 -0700] "GET /apache_pb.gif HTTP/1.0" 200 2326` (<https://httpd.apache.org/docs/2.4/logs.html>). Token positions: 1 IP, 2 identity, 3 user, 4 `[date`, 5 tz`]`, 6 `"VERB`, 7 URL-path, 8 `HTTP/x.x"`, 9 status, 10 bytes. **Field 7 is the URL path.** The `combined` format adds the referer and user-agent at the end, which does not disturb fields 1–10. The nginx module doc ships the whole combined string verbatim —

```nginx
log_format combined '$remote_addr - $remote_user [$time_local] "$request" $status $body_bytes_sent "$http_referer" "$http_user_agent"';
```

— so the combined extras are exactly the trailing two quoted values, and the same field-7 extraction applies unchanged (<https://nginx.org/en/docs/http/ngx_http_log_module.html>).

**The field map, so the pipeline above is readable.** Values annotated on the shape of the Apache docs' example line (the docs' own line uses `127.0.0.1`; annotations here are synthetic):

```text
field 1     203.0.113.9                     client IP (the docs' example writes 127.0.0.1)
fields 2-3  -                               identd identity, authenticated user
fields 4-5  [10/Oct/2000:13:55:36 -0700]
field 6     GET                             verb — POST is a collection point's habit
field 7     /apache_pb.gif                  request path — the field the recipe sorts on
field 8     HTTP/1.0"                       protocol, closing quote included
field 9     200                             status code
field 10    2326                            bytes sent
after 10    combined adds referer and user-agent as the trailing fields
```

**Verb/status pairings worth reading, labelled honestly.** Two recurring shapes on a publisher of other people's content, both observable from the same lines with no extra tooling. First, `POST`-concentrated paths: the field definition above means a collector such as Check Point's `store.php` must show up as one path repeating under `POST`, while your real pages stay `GET`-shaped — the definition is verified, the shape is an inference to confirm against your own log before acting on it. Second, status splits on one path: Fortra documents RatPressto blocking known scanner IPs and user-agents with a redirect to a real easternbank.com page, which in log shape reads as a single path whose responses split between a 30x for scanner-looking clients and a 200 for the rest — the redirect behavior is documented in the writeup (<https://fortra.com/blog/ratpressto-phishing-kit>); whether it appears in your log is your measurement to make, and Section 8's corroboration bar applies equally here.

**The cheap check, hand-tested.** Run on 2026-11-01 against a two-line synthetic CLF file (one Apache-origin example line from the Apache log doc, one forged). Output, exactly:

```text
      1 /wp-content/uploads/2025/11/sh.php
```

Command as it was run (against the synthetic file in `/tmp/oc-free`, not against a live server):

```bash
grep -rh 'HTTP/1.1"' /var/log/nginx /var/log/apache2 /var/log/httpd 2>/dev/null \
  | awk '{print $7}' | sort | uniq -c | sort -rn | head -20
```

Five caveats; the first two come from the test itself:

1. `grep 'HTTP/1.1"'` silently omits HTTP/1.0 request lines (the Apache doc's own example line is one). Widen to `grep -E 'HTTP/1\.[01]"'` to include both — the exact form used in the recipe below.
2. **The pipeline always exits 0**: `awk` succeeds on empty input, so the chain's exit code cannot distinguish "no matches" from "no logs read". Count what came out, don't trust the exit code.
3. **The live file is not the whole history.** Both Debian-family packages ship logrotate configuration — `apache2` ships `/etc/logrotate.d/apache2` and `nginx-common` ships `/etc/logrotate.d/nginx` (package file lists above) — so older access-history files exist on disk alongside the live file. The exact rotated filename suffix (e.g. `access.log.1` versus a date-stamped name) depends on the shipped logrotate config and is listed in [What I could not verify](#what-i-could-not-verify); sweep the directory, not only `access.log`.
4. **Buffered writes defer sync**: nginx's log module docs note buffered/gzip writes flush "when the internal buffer is full, or when the log file is rotated, or when the worker process is re-opening log files" (<https://nginx.org/en/docs/http/ngx_http_log_module.html>). History made seconds ago can be missing until the buffer drains.
5. **The ledger can be silenced by the operator who owns it — or by whoever edits the config.** `access_log off;` cancels the access log for the enclosing context, and nginx supports conditional (`if=`) logging; both are on the module doc's own page (<https://nginx.org/en/docs/http/ngx_http_log_module.html>). A config-edited hole in the access log is a data point in itself — a config file you did not change is a triage item, and it is not covered by the docroot sweeps in Section 3 because it lives in `/etc/nginx` or `/etc/httpd`.

## 3. What the document root looks like under you

**Document roots, by packaging.** The upstream Apache default is `DocumentRoot "/usr/local/apache/htdocs"` (<https://httpd.apache.org/docs/2.4/mod/core.html#documentroot>) — so the familiar `/var/www/html` is a distro convention, not Apache's. Where the convention comes from each family: Debian/Ubuntu's shipped `000-default.conf` makes `/var/www/html` the DocumentRoot default (<https://ubuntu.com/server/docs/how-to/web-services/configure-apache2-settings/>); Red Hat's RHEL 10 guide says "Optional: Add HTML files to the `/var/www/html/` directory" and warns the SELinux type `httpd_sys_content_t` applies by default to all content under `/var/www` (<https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/10/html/deploying_web_servers_and_reverse_proxies/setting-up-the-apache-http-web-server>); Debian's nginx package serves its placeholder out of `/usr/share/nginx/html/index.html` (<https://packages.debian.org/trixie/all/nginx-common/filelist>). **Find the real root instead of guessing it** — `httpd -S` "shows the settings as parsed from the config file (currently only shows the virtualhost settings)" (<https://httpd.apache.org/docs/2.4/programs/httpd.html>).

**The distributed config file is itself a payload surface.** Apache's core declares `AccessFileName .htaccess` as the default, and "while processing a request, the server looks for files with the name … in every directory of the path to the document" (<https://httpd.apache.org/docs/2.4/mod/core.html#accessfilename>). WordPress's own triage docs say exactly what to expect: `.htaccess` "is one of the more common files … most often updated and used for nefarious activities … located at the root of your installation folder, but can also be embedded within several other directories" (<https://wordpress.org/documentation/article/faq-my-site-was-hacked/>). And because "WordPress can overwrite anything between these tags" (`# BEGIN WordPress` / `# END WordPress`, <https://developer.wordpress.org/advanced-administration/security/hardening/>), an attacker's rewrite rules flourish outside the marker block, where WordPress itself never rewrites. **A payload can be ONLY this file** — no PHP, no shell — in which case the file-level `.php` sweeps below are blind and the log-level check in Section 2 is the one that survives.

**The override gate in front of that lane.** `.htaccess` content is honored only where `AllowOverride` permits it: `AccessFileName` is considered "in the event that `AllowOverride` is enabled for that directory", the default configuration ships `<Directory "/"> AllowOverride None </Directory>`, and with `AllowOverride` (and `AllowOverrideList`) set to `None`, ".htaccess files are completely ignored — the server will not even attempt to read `.htaccess` files in the filesystem" (<https://httpd.apache.org/docs/2.4/mod/core.html#allowoverride>). Read that the right way round for triage: on a server still at the shipped default, the rewrite-payload lane above is dead by configuration, and the surviving vectors are the log shape (Section 2) and the file inventory; where a WordPress-heavy host has widened override (the usual setup), the `.htaccess` lane re-opens. Either way the finding lives in your own `<Directory>` blocks — an override you did not enable on a web-writable path is the same class of config-edit as Section 2's `access_log off;` caveat.

**WordPress directories, and the one finding that needs no WordPress on your side.** The uploads base is `WP_CONTENT_DIR/uploads` by default, with year/month subfolders when `uploads_use_yearmonth_folders` is set (<https://developer.wordpress.org/reference/functions/wp_upload_dir/>); `/wp-content/` is per WordPress's hardening docs the one directory "intended to be writable by the web server process", containing `themes/`, `plugins/`, and the mu-plugins subcase (next bullet). The cheap triage for an operator who never installed WordPress: **`wp-content` exists under your docroot at all** is already the finding — you did not put it there, so someone did. The same hardening page also advises for triage: reinstall `wp-admin` and `wp-includes` from a fresh package, watch the `.php` files in `wp-content` specifically, and `DISALLOW_FILE_EDIT` to keep the built-in editor off (<https://developer.wordpress.org/advanced-administration/security/hardening/>).

**`wp-content/mu-plugins` — the directory the plugin list never shows.** WordPress's own handbook: must-use plugins "are automatically enabled on all sites in the installation … do not show in the default list of plugins on the **Plugins** screen … cannot be disabled from wp-admin", the directory is "**wp-content/mu-plugins** by default", can be armed "by uploading a PHP file to the mu-plugins directory", and "a compromised mu-plugin can be harder to notice than a normal plugin because it cannot be disabled from the main plugins list" (<https://developer.wordpress.org/advanced-administration/plugins/mu-plugins/>, page last modified 2026-10-14). The Check Point case used exactly this drop point for its REST-upload backdoor (`wp-sec.php`, hidden route `wp-json/wp-sec/v1/upload`, hardcoded creds, self-deleting installer, <https://research.checkpoint.com/2026/thousands-of-hacked-wordpress-sites-one-operation-unmasking-stopandprotect/>). Inventory the directory against what you (or your host) actually installed. The two cheap reads, with the docroot caveat above applied (adjust to what `httpd -S` shows):

```bash
# presence test — on a host that never ran WordPress, ANY output is the finding
find /var/www/html /usr/share/nginx/html -maxdepth 2 -name 'wp-content' 2>/dev/null
# the drop point the plugin list never shows — diff against what you (or your host) installed
ls -la /var/www/html/wp-content/mu-plugins/*.php 2>/dev/null
```

## 4. The named recipes for web shells

WordPress-specific inventory is one lane; the other lane generalizes, with published guidance that holds across web applications. NSA/ASD's **"Detect and Prevent Web Shell Malware"** (PP-20-0901, 21 April 2020) and MITRE ATT&CK's T1505.003 are the two standing references, and what they add on top of the file-sweep above is posture the WP docs do not carry:
- **Process lineage, not file mtime**: "web shells usually cause the web server process to exhibit unusual behavior". The guide's appendix G gives a working Linux recipe: after installing auditd, determine the web server uid — the guide instructs `apachectl -S`, whose output shows a line like `User: name="www-data" id=33` — then the whole recipe is the guide's three commands:

```bash
# NSA/ASD guide, appendix G, its own commands
apachectl -S                                                     # shows: User: name="www-data" id=33
-a always,exit -F arch=b64 -F uid=33 -S execve -k apacheexecve   # goes into /etc/audit/rules.d/audit.rules
cat /var/log/auditd/audit.* | grep "msg=audit(1581519503.841:47)"
```

Restart auditd after writing the rule. The log-read line targets the guide's launch table (`cat`, `crontab`, `hostname`, `netstat`, `uname`, `whoami`, …) as the flag list; ATT&CK states the same idea as detection analytic **DET0394/AN1109**: "File creation of unauthorized script (e.g., .php, .sh) in /var/www/html followed by execution of unexpected system utilities (e.g., curl, bash, nc) by apache/nginx" (<https://attack.mitre.org/techniques/T1505/003/>). Note the path clause names /var/www/html — the Ubuntu-family docroot — the same distro-prefix caveat Section 3 records for DocumentRoot.
- **"Known-good" diffing, with a timestamp caveat**: "The best method of detecting these web shells is to compare a verified benign version of the web application … against the production version" — the guide ships the one-liner `diff -r -q <known-good-image> <production-image>` as its appendix, and warns "administrators are cautioned against trusting timestamps on suspicious systems … attackers use a technique known as 'timestomping'" — the exact concern `checks/triage.sh` codifies as its D05 rule (mtime vs ctime divergence, logged at `delta > 3600s`).
- **The least-privilege countermeasure, restated as a tripwire**: "web applications should not have permission to write directly to a web accessible directory or modify web accessible code. Attackers are unable to upload a web shell to a vulnerable application if the web server blocks access to the web accessible directory." Note that WordPress's own hardening doc says `/wp-content/` is *by design* writable by the web server process — the two are in tension, and the auditd/data-based check above is how you carry the tripwire across that gap rather than fighting the design.
- **Signature-based file detection is the guide's weakest card**: "From the host perspective, signature-based detection is unreliable because web shells may be obfuscated and are easy to modify"; the guide keeps the list (China Chopper, WSO, C99, B374K, R57) only as an unmodified-deployments net, and its appendix-D Snort rules serve the same use case from the network side.
- **For the HTTP-log side**, the guide's appendix C ships a Python script that parses Apache access logs for "URLs with the least unique IP address or unique user-agents" (web-shell URIs are reached almost exclusively by a small handful of clients) — the same tail-window the one-liner in Section 2 covers at near-zero cost, from the other end of the sort.

## 5. TLS certificate issuance against your hostname

The ACME HTTP-01 challenge is a write that proves ownership. RFC 8555: the challenge identifier sits behind the fixed prefix `/.well-known/acme-challenge/` followed by the token (§8.3 and §9.2, <https://rfc-editor.org/rfc/rfc8555.html>), and the client's mainstream instruction is to "Provision files under .well-known on a web server for the domain" (§10.2). The same section carries the warning that matters on a shared or compromised host: "on a web server that allows non-administrative users to write to .well-known, any user can claim to own the web server's hostname by responding to an HTTP challenge". On this corpus's terms that sentence names the precondition: any application the web server can write for — a WordPress uploads pipeline above all — is a candidate author of files under `/.well-known/`, and each one that lands there is a claim on a hostname resolving to your IP.

What the host can see, cheaply: `ls` the `/.well-known/acme-challenge/` tree for each docroot and diff it against your own certificate-renewal schedule; a challenge file you did not cause is a hostname-claim attempt. The challenge itself is observable on your own side too: the path is fixed, so the write is a token file under each vhost's docroot (include `.well-known` in the `find` of recipe item 3) and the validation read-back is a `GET /.well-known/acme-challenge/<token>` line in the access log — a field-7 value in the map of Section 2. A challenge `GET` you cannot account for, or a token file still sitting in `/.well-known/` long past its validation window, is the host-side tail of the RFC's warning; recipe item 7 wraps all of this. Issued-cert visibility — which names a stranger has since certified against your IP, including names you never registered — is external-only, in Certificate Transparency: `external-vantage-and-honeypots.md` owns the crt.sh recipe and the passive-DNS check; do not duplicate them here.

## 6. The outside-in half (owned by the sibling file)

Two reads of the same phenomenon live outside this file's vantage, and `external-vantage-and-honeypots.md` owns both:

- **Which names resolve to, or were certified against, my IP** — a parked domain can point at your IP with no CDN involvement, or be `Host:`-routed to an nginx server-block you never wrote; passive DNS answers that from the outside (the mnemonic `api.mnemonic.no/pdns/v3/<IP>` recipe is that file's), and Certificate Transparency answers the certified-names question (its crt.sh recipe).
- **What a page looks like from a stranger's browser** — SNI-routed, CDN-fronted, or rewritten at the edge: `httpd -S` and your own nginx/Apache config show your side; what the edge serves from your IP to the rest of the world needs outside-in vantage (a vantage the same file covers with honeypots and external probes).

This file's remaining sections stay strictly on the host-owner side of that line.

## 7. AI-native edge platforms: the phishing-bait hoster with no host

Since 2025-01, Trend Micro has tracked fake-CAPTCHA pages on AI-native platform builders — the captcha screen is shown to the human visitor while the browser is redirected behind it to a credential-harvest page (Microsoft 365 in the reported cases), and scanners that do not pass the captcha see only the captcha. Counts at the 2025-09-19 report: **52 sites on `vercel.app`, 43 on `lovable.app`, 3 on `netlify.app`** (<https://www.trendmicro.com/en_us/research/25/i/ai-development-platforms-enable-fake-captcha-pages.html>). The platforms' own policies treat these uses as violations: Vercel's AUP bans projects that "Scrape, proxy, act as a VPN, or host media for hot-linking" and that "Rent, lease, loan, or sell access to … the Services … to any third party", lists phishing under impersonation clauses, and routes violations to "restrict, suspend, or terminate your access to Services immediately upon notice" (<https://vercel.com/legal/acceptable-use-policy>, last updated 2026-04-21); Netlify's AUP bans unsolicited messages, bars use "solely as a remote storage server" ("their account immediately terminated … files … permanently removed"), bans renting access, and requires lawful purposes (<https://www.netlify.com/legal/acceptable-use-policy/>, last updated 2023-03-08); Deno Deploy's free tier advertises 1M requests/month, 20 GiB egress/month, and 5 custom domains at $0 (<https://deno.com/deploy/pricing>). The corpus-relevant point closes the section: every host-side check in this file — access logs, docroot sweeps, mu-plugins inventory, auditd lineage, `/.well-known` triage — has NO surface here because there is no host of yours to inspect. The only operator vantage is external: CT logs carrying the subdomain names, passive DNS, abuse-report pipelines — `external-vantage-and-honeypots.md` owns that tier, and a page hosted there must be handled through the platform's report path, not this file's parsers.

## 8. Refutation: what would make each claim here wrong

The host-side claims read clean; the refutations to expect are about the boundaries:

- **"The access-log shape proves content hosting" — not by itself.** Legitimately forwarded correct traffic (a personal blog you own, proxied from another machine of yours) reproduces the identical `GET /…` line shape; the log is a shadow, not a verdict, and the finding needs corroborating file-level evidence. The discriminator: **mtime vs ctime**, which `checks/triage.sh` codifies as its D05 rule — "mtime is attacker-controlled; ctime is not, without a kernel rootkit" and it tags files whose mtime runs `$((delta / 3600))h` behind ctime on unowned paths. That echoes the NSA guide's timestomping warning almost word for word (Section 4), and it leaves the standing advice in place: "Detection methods for web shells may falsely flag benign files. When a potential web shell is detected, administrators should validate the file's origin and authenticity."
- **"The `.htaccess`-only payload hides from every check but one."** When the payload is nothing but a `.htaccess` rewrite/redirect (Section 3), `mu-plugins` and `wp-content` checks are silent, and so are the file sweeps; the log-shape check (Section 2) stays, because served lines exist whether the content came from a PHP file or a rewrite. The inverted gap matters equally: the document-root sweep can be blind to `/etc/nginx`-level log-silencing (Section 2, caveat 5), which no docroot sweep can see but a config diff does — keep the two vectors separate in triage, because one exposes what the other cannot. And each of these has a configuration gate the other does not: the rewrite lane only fires where `AllowOverride` permits (Section 3's override gate), so on a shipped-default server the `.htaccess`-only payload dies by configuration, not by triage.
- **"Web-shell file-level scanners catch it at the door" — the guides say the opposite**: "From the host perspective, signature-based detection is unreliable because web shells may be obfuscated and are easy to modify" (<https://media.defense.gov/2020/Jun/09/2002313081/-1/-1/0/CSI-DETECT-AND-PREVENT-WEB-SHELL-MALWARE-20200422.PDF>). This is why the file-level tier here is inventory (`mu-plugins`, `wp-content` presence, `.htaccess` outside markers) rather than content matching, and why the auditd process-lineage recipe is the one that scales.
- **"One interpreter is out of scope here."** A `python3 -m http.server`-style page drop — an interpreter serving pages instead of a packaged web server — is flagged by `checks/triage.sh`'s interpreter rule (inline/expression flags like `-m` on `python|node|perl|ruby|php|java|deno|bun|lua|Rscript` command lines), which is its own lane in that file; this file's recipes do not re-cover it, because here the premise is content served from a normal web server and its own log paths. The relay/amplifier role boundary (tor, open proxy, torrent, reflector) is `open-relays-amplification-reflectors.md`.

## Detection recipe (cheapest first)

Ordered by tool cost, not by certainty: items 1–2 read what is already on disk, 3–5 read files you own, 6–8 need config or kernel cooperation, 9–10 run entirely outside the host (their specifics are deferred to `external-vantage-and-honeypots.md`). Every item carries an **FP condition**, and the standing honesty rule from Section 8 applies to all of them: a passing run is a measurement, not a verdict.

1. **Access-log shape sweep, live files.** `grep -E 'HTTP/1\.[01]"' /var/log/nginx/access.log /var/log/nginx/access.log.* /var/log/apache2/*access* /var/log/httpd/*access_log* 2>/dev/null | awk '{print $7}' | sort | uniq -c | sort -rn | head -20` — a squatter's paths (kit downloads `.php`, `.well-known` writes, redirects, `Host:`-probed vhost hits) cluster at the top with counts nobody's legitimate audience produces. **FP condition**: real traffic from your own app, including bot crawls; act on the shape of the top entries, not on the count alone, and validate anything surprising against the docroot contents (item 3), the same corroborating file evidence Section 8 names.
2. **Rotation and volume sweep.** Same pipeline with the rotated files added, plus `wc -l` across the log set — the Debian-family packages both ship logrotate configs in `/etc/logrotate.d/`, so history exists on disk. **FP condition**: none over item 1 beyond the same; the separate run exists because a live-file-only check misses the payload's first day once rotation happens.
3. **Docroot file sweep.** `find <docroot> -name '.htaccess' -o -name '*.php'` against what you actually deployed, with mtime-vs-ctime cross-check per `checks/triage.sh`'s D05 rule. **FP condition**: real CMS self-updates and maintenance spurious — mtime alone is never the finding; the ctime-divergent pair is.
4. **The WordPress presence test.** `find /var/www/html -maxdepth 2 -name 'wp-content' 2>/dev/null` — on a host that never ran WordPress, existence is the finding. **FP condition**: you actually run WordPress on that vhost or host (then it is a directory, not a clue).
5. **`mu-plugins` inventory.** If WordPress is present, list `wp-content/mu-plugins/*.php` and diff against what you installed; anything else is the exact drop point documented as easier to miss than a normal plugin (<https://developer.wordpress.org/advanced-administration/plugins/mu-plugins/>). **FP condition**: hosting providers commonly drop `mu-plugins` themselves ("Web hosts commonly use mu-plugins") — compare against the host's docs or changelog before reacting.
6. **Process lineage (the auditd recipe).** Web-server uid `execve` watch: add `-a always,exit -F arch=b64 -F uid=<UID> -S execve -k apacheexecve` to `/etc/audit/rules.d/audit.rules` and flag non-application executables launched by the server process (`curl`, `bash`, `nc`, `uname`, `whoami`). **FP condition**: legit deploy hooks (`wp-cli`, composer, cron-wrapped maintenance) spawn as the same user during deploys — gate on agent path, not on process name.
7. **`/.well-known/acme-challenge/` triage.** `ls` the path under each docroot and diff against your own certificate-renewal schedule. Foreign challenge files equal foreign issuance claims against hostnames resolving to your IP (Section 5). **FP condition**: your own scheduled renewals (recheck around each issuance window ±1 day); also a wider-directory `.well-known` with unrelated, service-spec subdirectories is normal (RFC 8555 names a well-known zone, not a single path) — judge by the `acme-challenge` name only.
8. **Per-vhost log enumeration.** For Apache-family hosts with enabled additional sites (`/etc/apache2/sites-enabled/*`, `/etc/httpd/conf.d/*.conf`), list each vhost's `CustomLog`/`ErrorLog` targets and re-run item 1 against those paths (Section 2, per-vhost paragraph). **FP condition**: none beyond item 1; the run separates "no log because no vhost" from "no log because of log-silencing" (Section 2, caveat 5).
9. **External view (not duplicated here).** CT logs (`crt.sh`) and passive DNS (`api.mnemonic.no/pdns/v3/<IP>`) for names you did not register, per `external-vantage-and-honeypots.md`. **FP condition**: shared-hosting neighbors and intermediate-CA noise; check issuing CA, SANs and first-seen date before escalating.
10. **Edge-hosted content (no host-side path exists).** If someone reports your *name or brand* on a `vercel.app`/`netlify.app`/`lovable.app` page, the check is external-only (CT, passive DNS, the platform's report path) — `external-vantage-and-honeypots.md` owns this tier; host-side work is absent by definition (Section 7). **FP condition**: lookalike strings in CT entries from typo-parked domains; check certificate issuer and age first.
